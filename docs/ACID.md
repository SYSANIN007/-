# ACID и CRUD простыми словами — и как это работает в «ACID Wallet»

Этот документ — теоретическая часть к учебному приложению: что означают четыре буквы,
как их обеспечивает SQLite/Room и где в коде приложения это видно.

---

## 0. Что такое транзакция

Транзакция — это группа изменений базы, которая для всех остальных выглядит как одно
неделимое действие. В SQL это три команды:

```sql
BEGIN TRANSACTION;       -- начинаем; изменения пока никто не видит
  UPDATE accounts SET balanceCents = balanceCents - 30000 WHERE id = 1;
  INSERT INTO operations (accountId, amountCents, ...) VALUES (1, -30000, ...);
COMMIT;                  -- фиксируем: теперь изменения видны всем и они на диске

-- или, если что-то пошло не так:
ROLLBACK;                -- откатываем: в базе не осталось ничего
```

В приложении то же самое делается кодом (Room):

```kotlin
db.withTransaction {                 // BEGIN
    dao.updateBalance(from.id, newBalance)      // UPDATE
    dao.insertOperation(transferOutOperation)   // INSERT
    dao.updateBalance(to.id, newBalance)        // UPDATE
    dao.insertOperation(transferInOperation)    // INSERT
}                                    // COMMIT (или ROLLBACK, если было исключение)
```

Гарантии транзакций описывают словом **ACID** — это английская аббревиатура четырёх свойств.

---

## A — Atomicity (атомарность): «всё или ничего»

**Что значит.** Транзакция применяется целиком или не применяется вовсе. Промежуточного
состояния «половина транзакции в базе» не существует.

**Что было бы без неё.** Самый частый пример из жизни — перевод:

```kotlin
// ❌ ОПАСНО: две независимые транзакции на одну бизнес-операцию
db.withTransaction { debit(from, 300_00) }   // COMMIT — деньги уже списались
killProcess()                                // приложение упало / система убила процесс
db.withTransaction { credit(to, 300_00) }    // уже никогда не выполнится
```

Итог: со счёта списались 300 ₽, но получателю они не пришли. Деньги «висят» между счетами,
и починить это можно только компенсирующей операцией — или вообще никак, если журнала нет.

**Как спасает транзакция.** Обе половины внутри одного `BEGIN … COMMIT`:

```kotlin
// ✅ правильно
db.withTransaction {
    debit(from, 300_00)
    credit(to, 300_00)
}
```

Если между ними произойдёт исключение (или выключится питание), SQLite по журналу
транзакций (WAL) вернёт базу в состояние до `BEGIN`.

**Где посмотреть в приложении.** Вкладка **ACID → «Запустить эксперимент (3 шага)»**.
Эксперимент на служебном счёте делает три вещи и измеряет результат:

| Шаг | Код | Что остаётся в базе |
|---|---|---|
| 1 | две вставки журнала + изменение баланса внутри транзакции | всё: 2 строки журнала и новый баланс |
| 2 | изменение баланса без транзакции, затем сбой | ничего не откатывается: баланс уменьшился, записи в журнале нет (инвариант сломан!) |
| 3 | вставки журнала + изменение баланса, затем сбой внутри транзакции | ничего: ROLLBACK отменил все четыре запроса |

---

## C — Consistency (согласованность): «база всегда корректна»

**Что значит.** Транзакция переводит базу из одного корректного состояния в другое
корректное состояние. Все правила (инварианты) данных остаются выполненными.

**Какие инварианты в нашем приложении:**

1. **Баланс не бывает отрицательным.** Проверяется перед списанием и переводом:
   ```kotlin
   if (from.balanceCents < amountCents) throw WalletException.InsufficientFunds(...)
   ```
2. **Баланс счёта равен начальному остатку плюс сумма всех проведённых операций журнала:**
   ```
   balanceCents = initialBalanceCents + Σ(amountCents) по операциям со статусом ≠ CANCELLED
   ```
   Именно поэтому изменение баланса и запись в журнал всегда выполняются **вместе**.
   Проверить инвариант в любой момент можно кнопкой «Сверка журнала» — она пересчитывает
   балансы по журналу (`WalletRepository.recalculateBalances()`).
3. **Операция не может ссылаться на несуществующий счёт** — за это отвечает внешний ключ:
   ```sql
   FOREIGN KEY(accountId) REFERENCES accounts(id) ON DELETE CASCADE
   ```
   Удалили счёт — журнал уходит каскадом, «осиротевших» строк не остаётся.
   Чтобы это работало, база открывается с `PRAGMA foreign_keys = ON` (см. `AppDatabase.kt`).

**Важно понимать.** СУБД гарантирует сохранность *своих* правил (типы, ключи, уникальность).
А вот бизнес-правило «нельзя потратить больше, чем есть» — это уже ответственность
приложения, и проверять его надо внутри той же транзакции, в которой меняются данные.
Иначе между проверкой и записью кто-то успеет изменить баланс.

## I — Isolation (изоляция): «никто не видит незавершённого»

**Что значит.** Одновременно работающие транзакции не мешают друг другу так, как будто
они выполнялись по очереди. Результат параллельной работы должен совпадать с результатом
какого-то последовательного порядка.

**Какие бывают аномалии:**

| Аномалия | Что происходит |
|---|---|
| **Dirty read** (грязное чтение) | читаем данные, которые другая транзакция ещё не зафиксировала |
| **Non-repeatable read** (неповторяющееся чтение) | два одинаковых SELECT подряд дают разные данные |
| **Phantom read** (фантомное чтение) | между двумя запросами «появляются» новые строки |
| **Lost update** (потерянное обновление) | два потока читают одно значение и «затирают» изменения друг друга |

Классический lost update в кошельке:

```kotlin
// ❌ два потока одновременно меняют один счёт
// поток 1: читает 10 000 ₽        // поток 2: читает 10 000 ₽
// поток 1: пишет 9 000 ₽ (аренда) // поток 2: пишет 11 000 ₽ (зарплата)
// Итог: 11 000 ₽ вместо 12 000 ₽ или 9 000 ₽ — одно из изменений потеряно
val current = dao.findBalance(id)
dao.updateBalance(id, current + delta)
```

Правильно — читать и писать **в одной транзакции** (тогда внутри неё значение актуально):

```kotlin
db.withTransaction {
    val current = dao.findById(id)!!.balanceCents
    dao.updateBalance(id, current + delta)
}
```

**Как это устроено в SQLite.** Запись может идти только одна за раз: транзакция, которая
собирается писать, получает блокировку записи (`BEGIN IMMEDIATE`), остальные ждут.
Поэтому в SQLite уровень изоляции фактически **SERIALIZABLE** — самый строгий.

**Важная деталь — режим WAL.** База открывается так:

```kotlin
Room.databaseBuilder(context, AppDatabase::class.java, "acid_wallet.db")
    .setJournalMode(JournalMode.WRITE_AHEAD_LOGGING)
```

В режиме Write-Ahead Logging читатели работают со «снимком» базы и **не блокируют**
писателя, а писатель не блокирует читателей. Именно поэтому вкладка «Журнал» продолжает
показывать данные, пока идут транзакции.

**Где посмотреть в приложении.** Вкладка **ACID → «Запустить 4 опыта с изоляцией»**:

| Опыт | Что делаем | Что видно в отчёте |
|---|---|---|
| 1 | отчёт читает два счёта двумя отдельными запросами, параллельно идут переводы | сколько отчётов увидели «невозможное» состояние `A + B ≠ const` |
| 2 | то же чтение, но внутри одной транзакции | 0 противоречивых снимков |
| 3 | «зарплата» и «аренда» одного счёта без транзакции | деньги теряются или появляются «из воздуха» |
| 4 | то же, но каждое изменение внутри `db.withTransaction { }` | итог ровно 0 ₽: изменения не теряются |

Плюс вкладка **Демо-банк → «20 параллельных переводов по 1 ₽»** — стресс-тест изоляции
на настоящих счетах: 20 одновременных транзакций, сумма по счетам неизменна,
в журнале ровно по две записи на каждый успешный перевод.

## D — Durability (долговечность): «зафиксировано — значит сохранено»

**Что значит.** После успешного `COMMIT` данные уже не потеряются, даже если приложение
закрыть, процесс убить или выключить питание. За это отвечает журнал СУБД: изменения
сначала пишутся в него (и синхронизируются на диск), и только потом попадают в основной файл.

**В нашем приложении:** база работает в режиме WAL, то есть `COMMIT` означает запись
в WAL-файл, а `PRAGMA synchronous = NORMAL` (значение по умолчанию для WAL) — разумный
компромисс между скоростью и надёжностью: потеря при аварийном отключении ограничена
несколькими последними миллисекундами, а сама база не повреждается.

**Как проверить.** Вкладка **ACID → «Оставить отметку в журнале»**, затем:
1. полностью закрыть приложение (свайпом из списка недавних задач);
2. открыть снова.

Счётчик «Отметок долговечности в базе» сохранится — данные действительно лежат на диске,
а не в оперативной памяти. (Проверка честная: отметки пишутся в служебный журнал,
при этом режим WAL и `COMMIT` — самые настоящие.)

## Как это соотносится с CRUD

CRUD — это про то, **какие действия** бывают над данными, ACID — про то, **как**
эти действия гарантированно выполняются. В приложении видно, как они связаны:

| CRUD | SQL | Room | Транзакция нужна, потому что… |
|---|---|---|---|
| Create | `INSERT` | `@Insert` | при создании счёта вместе со строкой пишется системная запись журнала |
| Read | `SELECT` | `@Query`, `@Relation` | связанные данные нужно читать согласованно (одним снимком) |
| Update | `UPDATE` | `@Update`, `@Query("UPDATE …")` | баланс и журнал должны меняться вместе |
| Delete | `DELETE` | `@Delete`, `CASCADE` | удаление счёта и его журнала — тоже логически одно действие |

Правило приложения, которое видно во всём коде: **любое изменение денег выполняется
одной транзакцией вместе с записью в журнал**. Это и делает четыре свойства ACID
не теоретическими словами, а поведением, которое можно проверить кнопками.

---

## Мини-словарь

* **Инвариант** — правило, которое должно выполняться всегда (`баланс ≥ 0`).
* **WAL (Write-Ahead Logging)** — журнал предзаписи: изменения сначала пишутся в журнал.
* **Lost update** — потерянное обновление: результат одного изменения «затирается» другим.
* **Компенсирующая операция** — новая операция, которая «отменяет» последствия ошибочной
  (используется, когда откатить уже нельзя — например, деньги ушли во внешний банк).
* **Частичный индекс/уровень изоляции** — правила, которые определяют, что видят
  параллельные транзакции: `READ UNCOMMITTED`, `READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE`.
